## 設計書との意図的な差異

### D-1 保存先をサーバーのPostgreSQLにする

- 日付: 2026-11-04
- 判断: 授業データは、サーバーのPostgreSQLに保存する。
- 理由: 設計書は「利用者個人持ち(手元のファイルが正本)」だが、このリポジトリは公開デモとして動かすため、サーバー側の保存が必要。

- 補足: 余力があれば、確定データのJSON書き出し・読み込みを付けて、設計書の方針に寄せる。

### D-2 保存するのは自作・架空のサンプルだけ。30日で削除する

- 日付: 2026-11-04
- 判断: 保存は自作・架空のサンプルに限る。保存期限は30日。利用者が自分で全データを消せる。
- 理由: 設計書は、自作プリントの本文を保存してよいかを「要決定」にしている。決まるまでは、保存するデータを最小にする。
- 他の案: 期限なしで保存する(扱うデータの範囲が広がる)。
- 補足: 注意書きは、入力画面ではなく利用条件のページに書く(設計書の10/21の決定)。デモ画面には「サンプルデータ専用」の帯を出す。

### D-3 手法はサーバー側のルールで決め、AIは特徴の抽出と理由文だけを担当する

- 日付: 2026-11-04
- 判断: 活動の特徴(複数解法・基本範囲内・つまずきやすい・役割分担)をAIが抽出し、手法は決まった順序のコードで決める。
- 理由: 設計書は判断ロジックをサーバー側に置くとしている。同じ入力なら同じ結果になり、テストで固定できる。AIが誤っても、影響が特徴の抽出と理由文に限られる。
- 他の案: AIに手法まで決めさせる(結果が揺れ、テストで固定できない)。

### D-4 入力は貼り付けテキストだけにする

- 日付: 2026-11-04
- 判断: 画像・PDFの取り込みは作らない。
- 理由: 取り込み(OCR)は、それだけで大きな機能になる。ポートフォリオでは、設計から印刷までの1本の流れを優先する。

## 2-4 パスワードのハッシュ化

- argon2id を使う(総当たりに強く、メモリも使わせられるため)。パラメータは OWASP の推奨値で、テストで固定した。
- 最小12文字、最大128文字。最大を決めるのは、巨大な入力でサーバーを詰まらせる攻撃を防ぐため。文字種の縛りは付けない。規則は packages/shared に置き、画面と API で同じ判定を使う。

- パスワードは NFKC に正規化してから hash / verify する。端末や IME による文字表現の違いで、ログインできなくなるのを防ぐ。ユーザーが増えたあとに変えると既存のハッシュが合わなくなるため、今決めた。

## 2-5 セッション認証

- トークンは randomBytes(32)。Cookie にはその値、DB には SHA-256 のハッシュを保存する(DBが漏れても Cookie を偽造されないため)。パスワードと違い、トークンは十分に長いランダム値なので、遅いハッシュやソルトは要らない。
- 有効期限は7日の固定。使っても延長しない。期限切れの行は、見つけた時点で消す。2-11 のスクリプトは取りこぼしの掃除に使う。
- トークンは43文字の base64url の形式だけを受け付ける。形式が違う値は、DB を引かずに無効にする。
- Cookie は HttpOnly、SameSite=Lax、本番のみ Secure。
- Origin チェックは POST/PUT/PATCH/DELETE にかけ、許可リストに無い Origin と、Origin が無いリクエストは 403。GET は状態を変えない決まりにする。
- APP_ORIGIN は本番で必須。未設定なら起動時に例外にする(黙って開発用の値にすると、本番の POST が全部 403 になり、原因がログに出ない)。値は new URL().origin にそろえる(末尾の / やパスを許す)。
- store.find / remove の失敗は、握りつぶさず 500 として上に投げる。null は「セッションが無い・期限切れ」のときだけ。DB 障害中に全員がログアウト扱いになり、原因が見えなくなるのを防ぐため。
- 組み込みは buildApp() に切り出し、本物のアプリに inject でテストする。applySecurity は、ルートを登録するより前に呼ぶ。
- ロジックは SessionStore という窓口の後ろに置き、テストは偽の窓口で行う。Prisma につなぐ実装は、CI に prisma generate を足すときに作る(generated は Git 対象外なので、今 import すると CI の typecheck が落ちる)。
- 3-15 で確認すること: /api を転送するプロキシが、Origin ヘッダーをそのまま通しているか(書き換え・削除されると、正しい POST も 403 になる)。
- 未決(2-6 以降で決める): ログアウト時に Cookie も消すか。ログイン時に、古いセッションをどうするか(複数端末を許すか)。

## 2-6 認証API

- 入力は packages/shared の Zod スキーマで検証する。メールは前後の空白を除いて小文字にそろえる(PostgreSQL の unique は大文字小文字を区別するため)。ログインでは、パスワードの最小長を求めず、最大長だけ守る。
- ログイン失敗の文言は1種類。存在しないメールでも、ダミーのハッシュで検証を1回走らせて、返答の速さから登録の有無が分からないようにする。ダミーは起動時に1回だけ作る。
- 登録済みのメールは 409 で知らせる。メールの有無が分かってしまうが、確認メールの仕組みが無いと隠せないため、回数制限で抑える。登録済みと分かった時点で、重いハッシュ計算はしない。
- 負荷対策: argon2 の同時実行を2つまでにし、順番待ちは20まで。超えたら 503(本文は汎用)。IP ごとの回数制限に加えて、IP を問わない全体の上限(ログイン 600回/15分、登録 200回/1時間)も置く。全体の上限は、使い切られると一般の利用者も止まるので、余裕のある値にした。本当の防御は、デプロイ先のプロキシ側にも置く(9-4 で確認)。
- 全体の上限には、入力が正しいリクエストだけを数える(重い処理の前で判定する)。
- 登録した直後は、ログインした状態にする。
- 2-5 で未決にした項目: ログアウトでは DB の行と Cookie を消す。複数端末のログインは許す。ログイン時は、新しいセッションを作ってから、そのブラウザの古いセッションを消す(作成に失敗しても、古いセッションは残る)。
- 回数制限は IP アドレスごと。ログインは15分に10回、登録は1時間に5回。記録はメモリ上なので、再起動でリセットされ、台数が複数だと共有されない(いまは1台前提)。学校の共有 IP から、複数人が同時にログインすると、上限に当たる可能性がある。値は 9-4 で見直す。
- trustProxy は、true ではなく台数(TRUST_PROXY_HOPS)で指定する。true だと X-Forwarded-For を偽装されて、回数制限をすり抜けられるため。本番での値は 9-4 で確認する。
- 同意チェックは、2-6 の API では扱わない。スキーマに同意の記録を残す列が無いため、画面の 3-13 で、記録するかを決める。
- DB やハッシュ計算の失敗は、握りつぶさず 500 として返す(本文は汎用で、DB のエラー文は返さない。詳細はログに残す)。「DB 障害中に全員がログアウト扱いになる」「壊れたハッシュが『パスワード違い』になる」のを防ぐため。テストで固定した。
- ログ: Cookie と Authorization のヘッダー、Set-Cookie は、ログに出さない設定にした(標準のログはヘッダーを出さないので、設定変更に備える2重の防御)。実際のログに、パスワードとトークンが出ないことをテストで確認した。
- GET は、状態を変えない。SameSite=Lax の Cookie は、別サイトからの GET の移動でも送られるため。コードレビューのたびに確認する。/auth/me が状態を変えないことは、テストで固定した。
- DB への接続は db.ts で作り、ストアの Prisma 実装は prisma-stores.ts に置く。重複登録(P2002)の変換は、偽の Prisma でテストした。ルートのテストは偽のストアで行う。generated/ は Git に入らないので、CI に prisma generate を追加した(DATABASE_URL はダミー。generate は DB に接続しない)。

## 2-7 認証ミドルウェア

- 認証の確認は、requireAuth の1か所にまとめた。Cookie からセッションを引き、ユーザーを確かめ、request.user に入れる。
- 手順書の preHandler ではなく、onRequest で動かす。preHandler は、本文を読み込んだあとに動くので、未ログインの人にも、本文の解析をさせてしまうため。テストで固定した(壊れた JSON でも、未ログインなら 400 ではなく 401)。
- Origin チェック(全体の onRequest)が、requireAuth より先に動く。テストで固定した(未ログインで Origin が無い POST は、401 ではなく 403 で、Cookie も消さない)。
- 認証が要るルートは、registerProtectedRoutes の中にまとめ、フックをグループに1回だけ付ける。認証が要るルートを足すときは、このグループの中に書く。付け忘れは、テストで検出する(公開ルートの許可リスト以外は、未ログインで 401 になることを、全ルートで確かめる)。公開ルートを足すときは、許可リストに足す。
- 401 の本文は1種類(Cookie なし・不正・期限切れ・ユーザー消失のどれでも同じ)。
- 無効・期限切れの Cookie は、401 と一緒にブラウザから消す(死んだ Cookie で、毎回 DB を引かないように)。期限切れの行の削除は、掃除であって、利用者から見える状態の変更ではないので、「GET は状態を変えない」の例外としない。
- request.user には id と email だけを入れる。パスワードのハッシュは入れない(ログや応答に混ざらないように)。
- DB の失敗は、401 にせず、握りつぶさず 500。401 は「ログインしていない」ときだけ(DB 障害中に、全員がログアウト扱いになるのを防ぐ)。
- 4xx の本文は汎用にする。Fastify 自身の 4xx(壊れた JSON など)は、エラー文に入力の一部が入ることがあるため、`{ error: 'bad_request' }` などにする。自分たちで決めた本文(回数制限の 429)は、そのまま返す。
- trustProxy の台数は、境界をテストで固定した(1台なら末尾の IP だけを信用し、2台ならその1つ前まで信用する)。
- /auth/logout は、認証なしのまま(Cookie が無くても 204)。

## 2-12 スキーマの追加修正(11/5 レビュー・11/6 機能比較の反映)

- Lesson.status に GENERATING(生成中)を加えた。設計の実行中に、二重実行と編集を止めるため(5-7)。実行が途中で落ちると GENERATING のまま残るので、updatedAt からの経過時間で失敗扱いにする仕組みを、5-7 で作る。(未決: 時間の長さ)
- 列挙の値の追加(ADD VALUE)と、その値を使う変更(既定値や UPDATE)は、別のマイグレーションに分ける。PostgreSQL は、同じトランザクションの中で、追加した値を使えないため。
- Activity に (lessonId, position) の一意制約を付けた。同じ授業で、位置が重複しない。lessonId 単体のインデックスは、この一意制約の先頭の列で兼ねられるので、置き換えた(残すと、同じ検索用のインデックスが2つになる)。位置の更新では、一意制約のインデックスの更新も伴うが、1つの授業の活動は数十行なので、影響は小さい。
- 位置の入れ替えは、PostgreSQL が一意制約を行ごとにすぐ確かめるので、そのまま更新すると、途中で重複して失敗する。入れ替えと、設計の再実行による置き換えは、1つのトランザクションの中で、「いったん大きな値へ退避してから、最終の位置に設定する」か、「全削除してから作り直す」のどちらかで更新する。
- Issue に resolved(確認済み。既定は未確認)を加えた。確定時の警告は、未確認が残るときだけ出す(6-7)。
